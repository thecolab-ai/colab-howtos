## Run a 24/7 Hermes Agent on a DigitalOcean droplet

**What it is.** A self-hosted, always-on agent you can point at any model backend, with web search built in. JP moved his around-the-clock enrichment work onto it because he can pick any model for any job.

**How it works.** JP used the DigitalOcean one-click Hermes Agent installer plus the Hermes desktop client. You can attach as many model backends as you like. His agent fills in missing detail on listings on his own website through MCP tool calls. Hermes also comes with keyless Perplexity search, so you get web search with no setup.

The commands below come from Perplexity's Hermes integration guide, not from JP:

```bash
hermes update
hermes --version
hermes model                  # pick or add a model provider
hermes tools                  # reconfigure a tool's provider, then Web Search & Scraping, then Perplexity
hermes chat --toolsets web    # test the web tools
```

The basic "Fast Search" is free for Hermes users with no key. Standard search and page extraction need a Perplexity API key, which goes in `~/.hermes/.env`. The integration needs Hermes v0.21.1 (tag v2026.9.7) or later, so update first.

**Gotchas.**
- An agent running 24/7 with write access to your site can do a lot of damage quickly. Give its MCP tools the narrowest permissions that work and watch the first few runs.
- More throughput means more tokens. Watch your model spend.
- Treat the Perplexity key like a password and keep it out of anything you commit.

**Links.** Hermes Agent on DigitalOcean Marketplace: https://marketplace.digitalocean.com/apps/hermes-agent. Perplexity search in Hermes: https://docs.perplexity.ai/docs/getting-started/integrations/hermes

**Who shared it.** JP, after Suhel asked him to say more about his setup.

**Tested or not.** JP runs it. With hosted agents he got about 100 to 150 listings enriched every 12 hours, and Hermes has gone well past that, with throughput still climbing. He said he'd write up his setup properly. We haven't run the `hermes` commands, and the desktop client and MCP wiring were described without commands.

## Enforce a kid-friendly agent's guardrails in server-side code

**What it is.** A design rule for any agent a child will use: enforce the safety rules in server-side code, and treat the system prompt as a second line of defence. This is a technique we added from the chat. It wasn't in the original write-ups.

**How it works.** Alia piloted a kid-friendly chat agent at home and shared a guardrail pack with tests and results. Chris picked out the core rule: "Enforce, don't instruct". Fixed safety responses, session limits and allowed hours are served from server-side code rather than left to the model. The agent was also designed to recognise when someone is pushing against the guardrails and to hold firm, and the parent gets regular updates on any red flags.

A contributor would need to turn that into steps. Our outline, not something shared in the chat:
1. List the rules that must never fail (topics, session length, allowed hours, escalation to a parent) and implement each one in code that runs before and after the model call.
2. Keep a small set of fixed, pre-written responses for unsafe requests, and serve them from code instead of asking the model to improvise.
3. Then write the system prompt for tone, content and engagement, as the second layer.
4. Write tests that try to get around each rule, and run them on every change.
5. Log red flags and send them to the parent.

**Gotchas.**
- Safety and engagement pull against each other. Alia's big lesson was that a heavily scripted bot felt fake and didn't hold the user's interest. She ended up applying the same guardrails to a more natural-sounding agent.
- Jason asked about privacy. Alia said the pilot used the child's first name and age for context, and that anything bigger, or anything for schools, would need a proper look at data collection and where the data goes.
- Another member's warning: kids learn to get around guardrails. Test for that on purpose.

**Who shared it.** Alia, with Chris, Jason and others in the thread.

**Tested or not.** Alia ran a small pilot and said it has worked well so far. Her guardrail pack was shared as a file in the chat and isn't public, so the steps above are our outline and untested.

Want to turn this into a module? See [issue #8](https://github.com/thecolab-ai/colab-howtos/issues/8).

## Short captioned explainer videos from the Claude Managed Agents template

**What it is.** The Claude Console has a Managed Agents template, "Video explainer maker", that turns a topic and your source material into a 30 to 60 second captioned video with quiet background music. The scenes are drawn with code.

**How it works.** From the posted template config: you upload source material, and the agent takes facts only from what you give it. You choose an explainer (opens with a question, ends with the answer) or a promo (opens with a problem, ends with one call to action). It proposes a storyboard of 4 scenes by default, up to 8, each about 7 to 10 seconds, and says how many sub-agents it will run. After you approve, it works in three phases:
- Build: one agent per scene plus a music agent, in parallel. Scene agents check stills for clipping, overlap and contrast.
- Review: an independent agent flags at most one weak scene.
- Fix: runs only if a scene was flagged.

Outputs are `explainer.mp4`, a preview GIF under 2 MB and a PNG of stills. The config is set to Opus 5.5 at low effort, with multi-agent workflows on and only the file and bash tools enabled.

**Gotchas.**
- The music is synthesised with Python's standard library. If it comes out unusable, the template ships the video silent and says so.
- There's a 30-minute limit per run, and it asks before running anything bigger than its default size.
- Managed Agents sessions are stored server-side until you delete them and aren't zero-data-retention eligible. Don't upload anything sensitive.

**Links.** Managed Agents overview: https://platform.claude.com/docs/en/managed-agents/overview. Quickstart: https://platform.claude.com/docs/en/managed-agents/quickstart

**Who shared it.** Adam posted the template config in Show & Tell and said it's very good for making videos. The paste itself isn't linked here.

**Tested or not.** Untested by us. The details come from reading the config. The Console menu wording is our guess, so check the docs for the current flow.

Want to turn this into a module? See [issue #10](https://github.com/thecolab-ai/colab-howtos/issues/10).

## Steer a small open model by pushing single neurons

**What it is.** A small Python script that adds a push along one MLP neuron's output direction inside a 4B-parameter model while it generates, so you can watch a single neuron shift the model's tone or persona.

**How it works.** Caleb saw a claim that pushing one neuron in a Qwen 4B model turns it "evil", and tested it using the idea from Anthropic's persona vectors paper. He found candidate neurons by having the model role-play a trait and seeing which neurons in which layers lit up most. He published `steer.py` as a public gist. It runs with `uv`, which installs its own dependencies (Python 3.10 to 3.13, `torch`, `transformers` 5.x, `accelerate`). Neurons are written `L<layer>N<index>`, layers counted from 0, and a trailing `-` pushes the opposite way. Examples from the gist:

```bash
uv run steer.py --neuron L14N8949 --neuron L13N7956- "How was your day?"
uv run steer.py --model gemma --neuron L23N6283- --strength 1 "Tell me about the moon."
uv run steer.py --sweep --neuron L12N4619 "What do you think of my plan to open a bakery?"
```

`--sweep` runs strengths 0, 0.25, 0.5, 0.75, 1 and 1.5. `--recalibrate` recomputes the per-layer scale from a few calibration prompts. The default model is Qwen 3.5 4B. Gemma needs a Hugging Face login with the licence accepted. Expect about 9 GB for the model download.

**Gotchas.**
- The output is unfiltered. Caleb found that some neurons, pushed hard, produce hate speech, and he deliberately left those addresses out. Don't publish or deploy steered output.
- Big pushes make the model incoherent. Use the sweep to find the useful range.
- Adrian's point: when you change one part of a model, you test one small behaviour, but more than that has changed. Treat this as exploration, not a safe way to edit a model.
- Caleb expects the effect to be weaker in larger models.

**Links.** `steer.py` gist: https://gist.github.com/tuttinator/d1c874b9445a5a9ecf3da4c7967f6677. Persona vectors: https://www.anthropic.com/research/persona-vectors. uv: https://docs.astral.sh/uv/

**Who shared it.** Caleb, with Adrian in the thread.

**Tested or not.** Caleb said it works nicely on Apple Silicon. We haven't run it. The commands are copied from the gist.

Want to turn this into a module? See [issue #15](https://github.com/thecolab-ai/colab-howtos/issues/15).

## See what Claude Code and Codex are doing: live agent graphs

**What it is.** Ways to get a live picture of your agents at work: subagents spawning, parallel tasks, results flowing back to the orchestrator.

**How it works.** Steve asked for a "linked node" view. The thread gave four routes:
- **Just ask.** Suhel's tip: ask the agent for a lean HTML page built from its own session data. The harness already has all the data. He also runs a periodic review where the agent assesses how the two of them work together, and says it always turns up improvements.
- **Agent Flow** (from a ChatGPT answer Suhel pasted in). A live node graph for Claude Code and Codex. `npx agent-flow-app` opens it on port 3001. Needs Node.js 20+. There's also a VS Code extension.
- **Zoetrope** (same source). A terminal graph, live or replayed: `brew install furkankly/tap/zoetrope` or `cargo install zoetrope`, then `zoe` in a project, or `zoe <file.jsonl>` to replay a session.
- **Roll your own.** Tim runs a custom viewer on all his conversations that shows tool use, what was spawned and by whom, plus tool and skill counts. It reads from his session-log database (see the session logs section below).

**Gotchas.**
- The `npx` build of Agent Flow sends anonymous usage telemetry by default. Turn it off with `export AGENT_FLOW_TELEMETRY=false` or `export DO_NOT_TRACK=1`.
- Working out parent and child relationships from the logs is harder than drawing the graph.
- Session logs can hold secrets and client data, so keep any viewer local or behind auth.

**Links.** Agent Flow: https://github.com/patoles/agent-flow. Zoetrope: https://github.com/furkankly/zoetrope

**Who shared it.** Steve asked. Suhel and Tim answered, and Suhel also pasted a ChatGPT list of tools.

**Tested or not.** Nobody in the thread said they had run Agent Flow or Zoetrope. We checked both repos exist and took the commands from their READMEs. A VS Code extension called Agent Deck was also mentioned, which we haven't checked. Tim didn't share code for his viewer.

## Explainer videos from a Claude skill, with a voice clone or a free local voice

**What it is.** An agent turns a topic into a short narrated explainer video using a video skill (a `SKILL.md`), voiced by your own ElevenLabs clone or a free local TTS voice running on a CPU.

**How it works.** Steve had his agent analyse the election results as they stood and how things might play out, using Opus 5.5 on medium effort, then make an explainer. The video skill tells the agent how to storyboard, render scenes and add the voice-over. When he wants his own voice, he asks for the clone in the prompt. He used ElevenLabs' cheaper "instant" voice clone, which needed about 3 minutes of his voice. Steve uses these as "disposable" learning videos: watch once or twice to get a complex topic, then move on.

**Gotchas.**
- Only clone your own voice, or one whose owner has given explicit consent. Steve also raised the scam risk: a good clone can fool your family, so he's told his to ask probing questions if he ever calls with strange requests.
- Acronyms trip it up. Matt spotted the clone reading "ACT" as "A C T". Steve thinks ElevenLabs' edit feature could fix that. You can also respell words in the script you send to TTS.
- Quality varies run to run with the same clone, for no obvious reason.
- NZ place names came out well with the clone. Check te reo Māori and local names every time anyway.

**Cost.** Adam guessed under subscription pricing it would be a few dollars. Steve's screenshot put that video at USD 1.18. For personal disposable videos he recommends the free local voice, which he named as a "Phonon" model with the voice "Preston" and said was surprisingly good off a CPU. We couldn't confirm which project that is.

**Links.** ElevenLabs: https://elevenlabs.io. Claude Code skills: https://code.claude.com/docs/en/skills

**Who shared it.** Steve, with Matt, Adam, Kael and others in the thread.

**Tested or not.** Steve made and shared the video. His `SKILL.md` was shared as a file in the chat and isn't reproduced. A module would need a public video skill (the Managed Agents template above is one starting point).

## Skill stacking: a brand skill plus a video skill

**What it is.** Keep two separate skills, one that knows how to make explainer videos and one that holds a brand's guidelines, and load both for the same job. The video comes out in that brand's look without you touching the video skill.

**How it works.** Adam shared a course video he made by mixing a brand skill with a video explainer skill. Steve called it "skill stacking" and said agents seem to love brand-guideline docs. Adam added the payoff: you keep improving one video skill, and each brand gets its own brand skill. In practice:
1. Write the brand guidelines as their own skill, for example `.claude/skills/<brand-name>-brand/SKILL.md`, with logo and font or colour files beside it.
2. Keep the video skill brand-neutral: storyboarding, rendering, captions and audio only.
3. Name both skills in the prompt.
4. When the render drifts from the brand, tighten the brand skill, not the video skill.

**Gotchas.**
- If brand rules creep into the video skill, the two will contradict each other.
- Use real, current logo files. Don't let the agent redraw or guess a logo from an old document.
- If a brand needs a voice-over, only use a cloned voice with that person's consent.

**Links.** Claude Code skills: https://code.claude.com/docs/en/skills

**Who shared it.** Adam, with Steve.

**Tested or not.** Adam made a video this way. The folder layout follows the standard Claude Code skills layout. The chat didn't say how anyone laid out their own brand skills.

Want to turn this into a module? See [issue #14](https://github.com/thecolab-ai/colab-howtos/issues/14).

## Ship your Claude Code and Codex session logs into a database

**What it is.** Every Claude Code and Codex session is already written to disk as JSONL. Ship those files into a database and give your agents a tool to search it. The models can then look up what worked before, and when an agent breaks something you can trace exactly what happened.

**How it works.** Adam suggested it in Show & Tell. Jake said he uses it all the time, mostly for the confidence that he can trace what happened when an agent gets something wrong. Steve asked about storage: one member uses plain SQLite, and Postgres came up for when the data gets large. The general shape (our outline, since nobody shared code):
1. Find the logs. Claude Code keeps session transcripts under `~/.claude/projects/`. Codex writes `~/.codex/sessions/**/rollout-*.jsonl` (under `CODEX_HOME` if set).
2. Write a shipper that reads new lines and inserts one row per message or event, with session id, project or working directory, timestamp, role, tool name and text.
3. Start with SQLite and full-text search. Move to Postgres when it gets big or several machines write to it.
4. Optionally add embeddings for semantic search.
5. Give the agent a "search past sessions" tool (CLI or MCP) that returns snippets plus the session id, and a way to read around a hit.
6. Tell your agents in `CLAUDE.md` or `AGENTS.md` to search before starting something they've likely done before.

For live metrics and events on top, Claude Code can export OpenTelemetry. The monitoring docs' quick start sets:

```bash
export CLAUDE_CODE_ENABLE_TELEMETRY=1
export OTEL_METRICS_EXPORTER=otlp
export OTEL_LOGS_EXPORTER=otlp
export OTEL_EXPORTER_OTLP_PROTOCOL=grpc
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
```

Adam described where it leads next: once agents can see their own history, they can reflect on what went wrong and write new skills or rules. He called it "dreaming" and auto skill creation. Nobody posted steps for that part.

**Gotchas.**
- The database fills up fast, especially with high-dimension embeddings. Gligor raised it, and the thread's example of what not to do was embedding the message "ok" as a 1024-dimension vector. Filter before you embed.
- Session logs hold everything: file contents, command output and sometimes secrets or customer data. Keep the database private, and redact or skip tool output that might hold credentials.
- OTEL prompt content is redacted by default. `OTEL_LOG_USER_PROMPTS=1` turns it on, so think before you enable it.
- JSONL formats change between CLI versions. Store the raw line alongside your parsed columns.

**Links.** Claude Code monitoring: https://code.claude.com/docs/en/monitoring-usage. SQLite FTS5: https://www.sqlite.org/fts5.html. pgvector: https://github.com/pgvector/pgvector

**Who shared it.** Adam, Jake, Steve and Gligor.

**Tested or not.** Members run their own versions, but no shipper code or schema was shared. Steps 2 to 6 are our outline. The paths match the Agent Flow README and the OTEL variables match the Claude Code monitoring docs.

Want to turn this into a module? See [issue #13](https://github.com/thecolab-ai/colab-howtos/issues/13).

## Have Claude build an Android TV app, sideload it over ADB, then hill-climb a latency metric

**What it is.** Jake had Claude build him a native Android TV app that's much snappier than the stock apps, and let Claude install it on a Google TV Streamer itself over ADB. Then he gave Claude one number to improve, the time from switching streams to the first frame on screen, and left it iterating overnight. Claude's opening attempt took 1.85 s. By morning it was 0.84 s.

**How it works.** Our outline of a loop that fits what Jake described:
1. On the TV, turn on Developer options (Settings, System, About, then click Android TV OS build seven times) and enable USB or network debugging. Menu names vary by device.
2. Connect from your computer, for network debugging on port 5555:
   ```bash
   adb connect <device-ip>:5555
   ```
   Accept the prompt on the TV. Newer devices may want `adb pair` first.
3. Ask Claude to scaffold the app (D-pad navigation, a leanback launcher entry) and build an APK.
4. Let Claude install and relaunch it each iteration:
   ```bash
   adb install -r app-debug.apk
   ```
5. Pick one metric and a way to measure it on the device. Have the app log timestamps and read them back with `adb logcat`.
6. Give Claude the loop: change one thing, build, install, measure several times, keep the change only if the median improves, and record every attempt in a results file.
7. In the morning, read the results file and review the diff.

**Gotchas.**
- Measure on the real device, not an emulator.
- Take several samples per change. A single stream switch is noisy, and the agent will otherwise "win" on luck.
- Pin the metric and the test content before you start, so the agent can't improve the number by changing what it measures.
- Leave network debugging on only while you're developing.
- Only play content you have the rights to, such as your own media or public test streams.

**Links.** adb: https://developer.android.com/tools/adb. Run apps on a hardware device: https://developer.android.com/studio/run/device. Android TV guides: https://developer.android.com/training/tv

**Who shared it.** Jake.

**Tested or not.** Jake shared the result and that Claude does the APK sideloading. He didn't share the prompt, the code or how he timed it, so steps 3 to 6 are our outline. `adb connect` and `adb install` are standard commands from the Android docs.

Want to turn this into a module? See [issue #3](https://github.com/thecolab-ai/colab-howtos/issues/3).

## Also discussed

- **Reviews that are allowed to find nothing.** In a long thread on adversarial reviews, Suhel said Opus still misses things and other models regularly find gaps in its approach. Another member noted every model finds something to change in every other model's work, because we ask them to review and they feel they must find something. Their fix: say in the prompt that "no findings" is an acceptable result.
- **Claude Code settings and secrets.** When you approve a command with "Yes, and don't ask again", Claude Code saves that exact command to `.claude/settings.local.json`, so a command with a key or password in it saves the secret too. Security researchers found that file committed to public GitHub repos with live secrets in it. Claude Code keeps the file out of git when it creates it, but check yours is ignored, rotate anything that was committed, and pass secrets as environment variables instead of typing them into commands: https://code.claude.com/docs/en/permissions. In the chat, Steve's response was to make repos private by default, and JP has set up a separate GitHub account for agent-heavy projects.
- **Message threads (beta).** A member pointed at Anthropic's new message threads docs: https://platform.claude.com/docs/en/build-with-claude/message-threads. The conversation, system prompt and tools stay on Anthropic's side, so each request sends only the new turn. The docs add that thread contents are deleted within an hour of last use and aren't zero-data-retention eligible. Separately, Suhel wished agents would offer to move work into a fresh thread with the right context once a thread gets long.
- **ChatGPT and Codex usage: one allowance?** Dan read OpenAI's plan change as putting ChatGPT and Codex usage into one allowance, which would close the old fallback of using ChatGPT when Codex hit its limit. Others thought instant-effort chat might still be free. Check the current usage-limit doc for your plan.
- **Decision models.** Looking for alternatives to a hosted "rank and choose" model, members pointed at Clef from Cloudflare and Liquid AI's LFM decision models (https://docs.liquid.ai/lfm/models/decision-models), plus last week's classifier comparison. Nobody had hosted the Liquid model yet.
- **Cheap data gathering with Apify.** Steve said most of his data sourcing now fits in Apify's free tier, with actors called from agent skills to collect details and then other skills writing promo copy and images. Check each site's terms before you scrape it, and privacy law too if you're collecting details about people.
- **LLMs editing model weights.** The "weight-space programming" research got a lot of attention: https://rikiyat.github.io/blog/weight-space-programming/
- **Image generation with reference images.** OpenAI's Images 2.6 (https://openai.com/index/introducing-images-2-6/) can make GIFs and take reference images. One member used it to make character assets for a game.
- **Other links.** Node 26 is now LTS, worth planning an upgrade. Theo's `tstack` setup (https://github.com/t3dotgg/tstack). session-lens, a Claude Code mod a member built to show where tokens went and how long an agent runs before it needs you. A University of Auckland paper on where the bottleneck moves when AI writes the code (https://researchspace.auckland.ac.nz/items/a8dcfac9-1995-497d-9230-4917738b2483).
