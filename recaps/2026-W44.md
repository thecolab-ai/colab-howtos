A busy week in The Colab chats. ## Route GitHub issues to the right model and run them through Codex CLI

**What it is.** A small home-made "runner" that reads GitHub issues, asks a model which model and reasoning effort each issue needs, then hands the implementation to Codex CLI on a ChatGPT subscription.

**How it works.** The thread started with a complaint that the labs keep shipping more models with different strengths instead of one orchestrator. Bart's point was cost: routers like OpenRouter or Microsoft Foundry bill through the API, and for his workloads he reckons that would cost 10 to 20 times more than subscription limits. So he built his own. The loop is:

1. Fetch the issues you want worked on (for example by label) with the GitHub CLI or API.
2. Send each issue to a model with a fixed pre-prompt: how complex is this, and which model and effort should handle it? Ask for a short, structured answer your script can parse.
3. Start Codex non-interactively on the issue with that model and effort. Codex CLI has `codex exec` for scripted runs. Look up the current flags for model and effort in the Codex docs rather than guessing.
4. Review the result like any other change: tests, diff, PR.
5. Move on to the next issue.

**Gotchas.**
- It doesn't solve context. Each run starts fresh, so the issue text has to carry everything.
- Plan rules move. On 1 Nov OpenAI updated its ChatGPT and Codex usage-limit docs, and members read it as a move towards a set token allowance per plan, though the docs don't give numbers. Check your plan before you point a batch job at it.

**Links.** Codex CLI docs: https://learn.chatgpt.com/docs/codex/cli. GitHub CLI manual: https://cli.github.com/manual/. Usage limits: https://help.openai.com/en/articles/20001625-understanding-chatgpt-and-codex-usage-limits

**Who shared it.** Bart built and described it. Tim and others joined the thread about model orchestration.

**Tested or not.** Bart said it worked reasonably well, and that it should really be built into the tools. No code was shared, so the script structure above is our outline.

Want to turn this into a module? See [issue #6](https://github.com/thecolab-ai/colab-howtos/issues/6).

## Strip your agent scaffolding back, then add skills that spawn reviewers

**What it is.** Two related habits for coding agents. One: when a new model lands, run it bare to find out what it does on its own, then add scaffolding back one piece at a time. Two: instead of a fixed roster of named subagents, keep repo-level skills, some of which tell the agent to spawn a fresh agent with a specific review skill.

**How it works.**
- **Nude mode.** Steve has been running more and more in what he calls "nude mode": no skills, no `CLAUDE.md`, and now no subagents either. Jake described the goal as working back to a "minimum viable scaffold". Suhel's version: throw everything away with each new model, then reintroduce it in a controlled way to see what is still needed. In practice, move your skills and instruction files aside (don't delete them), work normally for a while, note where the model falls over, and add back only what fixes a problem you saw.
- **Skills that spawn reviewers.** Another member skips defined subagents. Any agent instance can use the skills, and some skills are workflows that say "spawn a new agent with this skill" for a bug, security or design review of a new feature. The key detail is strictly defined handoff data shapes: exactly what goes to the reviewer and what comes back. They keep skills repo-specific and copy them across to new projects, then adjust.

**Gotchas.**
- Measuring this burns tokens, because you're running similar work more than once. Nobody had a better measure than trial and error.
- Memory features can make a model over-weight old, random requests. Steve flagged this. If results go odd, try a session with memory off where your tool allows it.
- Don't skip review. Suhel said adversarial reviews still regularly find critical problems in code Claude or Codex wrote, with Claude sometimes missing things or overbuilding.

**Links.** Claude skills overview: https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview

**Who shared it.** Steve, Jake, Suhel and one other member.

**Tested or not.** Untested as a method. Nobody shared a way to measure whether bare beats heavy beyond trial and error.

## Drive Claude Code, Codex and other agents from one UI with T3 Code

**What it is.** T3 Code is an open-source control surface for coding agents on your own machine. It runs several agent harnesses on your existing subscriptions, shows their rate limits side by side, and lets you carry on from your phone.

**How it works.** Install and sign in to each agent CLI first (the README gives `codex login` for Codex and `claude auth login` for Claude Code). Then install T3 Code. The README lists:

```
curl -fsSL https://t3.codes/install.sh | sh
t3
```

or `npx t3@latest` to try it without installing, or a desktop package such as `brew install --cask t3-code`. `t3 service install` keeps it running in the background so your phone can reach it. In a chat you pick a harness, and you can mix harnesses in one chat.

The feature Suhel pointed out a day later: when you hit a rate limit, T3 Code pauses the work and resumes it at reset. You still get the warning, just in orange instead of red.

**Gotchas.**
- The project calls itself early and buggy.
- Read any `curl | sh` script before you run it.
- Auto-resume keeps spending your allowance after every reset. Watch long runs.

**Links.** Repo: https://github.com/pingdotgg/t3code. Site: https://t3.codes/

**Who shared it.** Suhel.

**Tested or not.** Suhel installed and used it, including the pause and resume. The install commands come from the README, not the chat.

## Turn a messy second brain into a structured context library for AI

**What it is.** A way to rescue a second-brain notes system that has grown into a tangle, by reshaping it into small, consistently structured markdown notes an AI can load as context.

**How it works.** Shakeel asked whether anyone was still getting value from their second brain now that the graph was unreadable. A member replied with their method: break project knowledge into individual notes (they call them "neurons"), each following the same structure. For book quotes that might be quote, book, category, domain, author and year. Then use the library to give AI context that is already classified. Raw input, such as meeting notes, goes through fixed templates (for example into "feature idea" notes), ideally as a regular routine so it doesn't pile up again.

Amanda asked how they built it. The answer: Notion hit its limits quickly, so they moved to local `.md` files, with Obsidian to link them (though they don't use the graph much).

Adam added the hosting idea: keep your memory local and under your control, then expose it as an MCP server or an API so any platform or model can use it. Switching tools then doesn't mean rebuilding your memory.

**Gotchas.**
- The 3D graph view looks good but wasn't what made it useful. The structure and templates were.
- Retrieval is now the main use for some people, so design for search and context-loading before browsing.

**Links.** Obsidian: https://obsidian.md/. Model Context Protocol: https://modelcontextprotocol.io/

**Who shared it.** The method came from one member. Adam suggested the self-hosted MCP or API layer. Shakeel and Amanda asked the questions.

**Tested or not.** The member said the method works for them, and Shakeel is trying it. No specific MCP server or code was shared, so that part is untested.

## Run a hackathon that actually produces something

**What it is.** A runbook for organising a hackathon, treating it as one stage in a pipeline rather than a one-off day.

**How it works.** Matt asked for highlights and lowlights. Klaus, who has run 13 hackathons and taken part in about 20, gave the list:
- Write really good challenge statements, and have a subject-matter expert in the room for each one. He runs a pre-event "mapathon" to map out and write the challenge statements with the people who own them.
- Curate participants so the skill mix matches the challenges.
- Set clear judging and submission criteria, keep them simple and fair, and don't change them during the day.
- Rotate mentors and facilitators around the teams to help with team dynamics, splitting up work and time management, especially leaving enough time for the demo and presentation.
- Decide before the event what happens to good ideas afterwards. If you don't, you get abandoned ideas and burn the goodwill of the people who came.

Adam, who has helped organise a couple recently, added that having repos, problem statements and data sorted beforehand gets people building straight away.

**Gotchas.** Klaus's list of what doesn't work: vague IP terms, too much sugary food, loud rooms, poor tables, too few power points. Bad Wi-Fi on its own can sink the event.

**Who shared it.** Klaus and Adam, answering Matt.

**Tested or not.** This is experience, not a tool. Matt said it filled gaps in his planning.

## Build a writing voice file so AI copy sounds like you

**What it is.** A reusable voice file (a skill, a project instruction or a plain markdown file) built from your own writing, so drafts come back sounding like you.

**How it works.** Tim asked what people use to get copy that sounds human. Chris described his setup:
- He built it from his own unassisted writing (work chat, emails, posts), not from a description of how he thinks he writes.
- It has a handful of hard rules that apply everywhere.
- It has a register per channel and audience, because a note to your boss reads nothing like a LinkedIn post.
- It includes real samples of his writing, and the samples win when they conflict with the rules.
- It has a check the model runs on every draft before handing it back.
- He adds to it every time he accepts or rejects an edit, so it becomes a record of how he actually sounds and what he keeps correcting.

His main finding: the biggest gains came from the banned list (specific words, keynote-style constructions, tidy summary lines at the end), not from style guidance. AI-sounding copy is mostly a pattern problem, and removing patterns gets you further than asking for a "human" tone.

**Gotchas.**
- If you seed it with writing that was already AI-assisted, you bake those habits in.
- One voice for every audience falls flat.

**Links.** Claude skills overview: https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview

**Who shared it.** Chris, answering Tim.

**Tested or not.** Chris uses it. No tool or file format was named, so the layout in a module would be ours.

## Check a site is readable by AI search (AEO checklist)

**What it is.** A checklist for making a personal or small-business site easy for search engines and AI answer engines to read, trust and cite. It came out of Chris asking a couple of AI agents to do an SEO and AEO (answer engine optimisation) review of his personal site. The reviews agreed with each other, and his summary was that they were technically correct and the remaining work was backing up claims and writing content.

**How it works.** Generalised from the reviews:
1. Every page has its own title, meta description, canonical URL and social preview tags.
2. JSON-LD structured data says who you are (a Person or Organization record), with Article markup and dates on posts.
3. `robots.txt` and a sitemap exist and work. Consider `llms.txt`, Markdown versions of key pages and an RSS feed.
4. `robots.txt` doesn't block GPTBot, ClaudeBot or PerplexityBot, and those crawlers get a normal page, not an error. Missing pages return a real 404.
5. Both the www and bare domain load, with one 301-redirecting to the other.
6. Other sites back up who you are: employer, meetup or event pages link to you, your structured data links back, and maybe a Wikidata entry.
7. If you share a name with someone better known, say which one you are.
8. Small tidy-ups: name in the homepage heading, "last updated" dates, About in the main menu, breadcrumbs.
9. Keep publishing. A stale site looks stale to answer engines too.

**Gotchas.**
- Being crawlable doesn't mean you'll be retrieved or cited. Another member shared an NZ audit making that point the same day.
- In practice the off-site work (other pages confirming your claims) mattered more than on-page fixes.

**Links.** llms.txt proposal: https://llmstxt.org/. Google structured data intro: https://developers.google.com/search/docs/appearance/structured-data/intro-structured-data. NZ audit article: https://itbrief.co.nz/story/aiready-audit-finds-many-nz-sites-hard-for-crawlers

**Who shared it.** Chris, plus the member who shared the itbrief article.

**Tested or not.** The findings came from agents, and Chris confirmed the technical points. How to test crawler access (for example, requests with each bot's user agent) wasn't shown in the chat, so that would be ours.

## Set up a code oracle so non-engineers can ask about your codebase

**What it is.** A way for product, support and business people to ask plain-English questions about the product ("why can't we have X on this form?", "what would it take to localise?") without pulling an engineer off their work.

**How it works.** Richard asked whether anyone had built one. Two answers:
- **Knowledge graph with Understand Anything.** Nara tried it for exactly this and made it the standard tool for their team. They ask business-logic and capability questions in plain English, and when the devs don't know, they ask the tool and then get a dev to confirm. The project's site gives these Claude Code plugin commands:
  ```
  /plugin marketplace add Egonex-AI/Understand-Anything
  /plugin install understand-anything
  /understand
  ```
  It also lists support for Codex, OpenCode, Gemini CLI and others.
- **Agent CLI behind a Slack bot.** Suhel's approach: put Claude Code, Codex or Cursor CLI on a Linux VM or spare box, give it access to whatever sources make sense (repos, read-only if that's all you need, plus help pages), and connect it to a Slack bot in the relevant channels. Everyone can ask from any device and learn from each other's questions. Teams should work too.

**Gotchas.**
- Nara found Claude very token hungry when generating the graph over a large set of repos, so they generated it with ChatGPT. The graph is JSON, so either model can read it afterwards.
- Treat answers as a strong first draft and confirm the important ones with a dev.
- Think hard about what the Slack agent can touch. Suhel mentioned a startup whose Slack agent also raises PRs, which is a much bigger trust step than read-only.

**Links.** Understand Anything: https://understand-anything.com/ and https://github.com/Egonex-AI/Understand-Anything. Slack apps: https://docs.slack.dev/

**Who shared it.** Nara and Suhel, answering Richard.

**Tested or not.** Nara uses Understand Anything with their team. Suhel runs the Slack setup for personal use. No Slack bot code was shared, so the wiring is untested and the install commands come from the project site, not the chat.
